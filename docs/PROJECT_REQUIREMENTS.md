# OOTD 立体日记——项目需求文档

> 文档版本：v1.2  
> 更新日期：2026-08-24  
> 当前阶段：MVP 定义  
> 产品范围：拍照/上传 → 生成每日 OOTD 形象 → 记录/分享

## 1. 项目概述

### 1.1 产品名称

暂定名：**OOTD 立体日记**

正式品牌名、Logo 和视觉识别系统不属于当前阶段的阻塞项。

### 1.2 一句话定义

> 每天拍一张，把今天的穿搭变成立体 OOTD，并自动收藏和分享。

### 1.3 产品定位

本产品是一款以女性用户为主要目标人群的轻量穿搭记录应用。用户无需预先创建数字人、整理衣橱或录入服装，只需拍摄或上传一张当日全身穿搭照片，即可生成具有统一审美和立体展示效果的 OOTD 数字形象，并按日期保存或分享到其他平台。

MVP 不是数字衣橱、虚拟试衣或社交社区。第一阶段只验证一个核心闭环：

```text
拍照 / 相册上传
        ↓
生成今日 OOTD 立体形象
        ↓
记录到日期 / 分享
```

## 2. 背景与机会

目前用户记录穿搭通常使用手机相册、社交平台或普通日记。这些方式虽然方便，但存在以下问题：

- 每日穿搭照片分散在相册中，长期回顾体验较弱；
- 普通照片缺少统一的视觉表现和收藏感；
- 记录工具往往要求填写标签或手动整理，操作成本较高；
- 传统数字衣橱需要逐件录入衣服，用户容易在获得价值前流失；
- 完整虚拟试衣技术复杂，但并非“记录今天穿了什么”的必要条件。

本产品通过“低门槛拍照 + 有惊喜感的形象生成 + 日历式积累”建立每日使用习惯。

## 3. 产品目标

### 3.1 MVP 目标

1. 用户可以在很少操作的情况下完成一次 OOTD 记录。
2. 生成结果足够好看、具有本人和当日服装的辨识度。
3. 生成结果具有收藏价值，用户愿意第二天继续记录。
4. 用户可以方便地保存或分享静态图片，并在结果页主动转动查看立体资产。
5. 验证“立体形象”是否比普通照片更能促进留存和分享。

### 3.2 用户价值

- **方便**：不用创建数字人，不用录入衣服，拍照即可。
- **好看**：将普通穿搭照片转换成风格统一的 OOTD 形象。
- **有积累感**：每天完成记录后点亮日历，逐渐形成个人穿搭时间线。
- **可表达**：将生成结果制作成适合朋友圈、小红书等渠道的分享内容。
- **默认私密**：原图和历史记录默认仅用户本人可见。

### 3.3 MVP 成功标准

产品上线测试后，优先验证：

- 首次上传至成功生成的完成率；
- 生成结果的保存率；
- 生成结果的分享率；
- 次日留存和 7 日留存；
- 用户每周平均记录次数；
- 用户对“好不好看”“像不像本人”“衣服像不像”的评分；
- 生成失败、重新生成和主动删除的比例。

具体数值目标应在确定测试规模、获客渠道和生成成本后补充，不在本版文档中虚构。

## 4. 目标用户与场景

### 4.1 核心用户

- 喜欢记录每日形象和穿搭的年轻女性；
- 经常自拍、拍全身照或发布 OOTD 内容；
- 重视审美、仪式感、个人表达与数字收藏；
- 希望记录穿搭，但不愿意花时间手工整理衣橱。

产品不限制其他性别使用，界面和模型能力应避免排他性表达。

### 4.2 核心场景

1. 出门前或到达目的地后，拍摄今日全身穿搭并生成 OOTD。
2. 从手机相册选择当天已经拍好的照片进行生成。
3. 在日历或时间线中回顾过去一周、一个月的穿搭。
4. 将今日 OOTD 以静态分享卡片保存到相册或分享到外部平台。

## 5. 产品原则

1. **先获得结果，再要求投入**：不在生成第一个 OOTD 前要求创建数字人或录入衣服。
2. **少输入**：除选择照片外，不强迫用户填写标签、身高、三围或服装信息。
3. **结果优先**：生成结果页是整个产品的核心体验和主要设计投入点。
4. **美感优先于测量精度**：MVP 不是身材测量或尺码判断工具。
5. **诚实表达能力边界**：单张照片看不到的背面和遮挡区域属于 AI 推测，不能宣传为精确还原。
6. **原图默认私密**：分享时默认只导出生成结果，不自动暴露原始照片、位置或其他敏感信息。
7. **不评价身体**：不提供身材打分、胖瘦评价或引发身体焦虑的文案。

## 6. MVP 范围

### 6.1 P0：必须实现

- 拍摄全身照片；
- 从系统相册选择照片；
- 拍摄/图片质量检查；
- 提交生成任务；
- 显示生成进度和任务状态；
- 生成今日 OOTD 立体形象；
- 查看生成结果；
- 输出可实时渲染的立体资产，支持用户通过手势在允许范围内主动转动查看；
- 生成失败后重试；
- 按日期保存记录；
- 日历查看历史记录；
- 时间线查看历史记录；
- 导出静态分享卡片；
- 删除原始照片、生成结果或整条记录；
- 基础账户和跨设备保存能力；
- 隐私说明、用户授权和数据删除入口。

### 6.2 P1：MVP 稳定后可加入

- 更换分享卡片背景、底座或模板；
- 添加一句话、心情或场景标签；
- 当日天气信息；
- 多种形象视觉风格；
- 同一天保存多个 OOTD；
- 一周/月度穿搭回顾；
- 原图与生成形象的对比分享模板；
- 基于实时模型额外导出短动态分享内容；
- 生成高清版本完成后的系统通知。

### 6.3 当前明确不做

- 首次进入时创建个人数字人；
- 上传正面、侧面、背面照片建立精确分身；
- 数字衣橱和逐件服装录入；
- 电商链接导入；
- 自定义上下装搭配；
- 虚拟试衣、尺码判断和合身建议；
- 真实布料物理模拟；
- 实时 AR 换装；
- 社区信息流、关注、点赞和评论；
- 穿搭评分、身材评分或审美排名；
- 面向品牌方的 3D 服装资产平台。

以上能力可以作为长期方向，但不能挤占 MVP 核心闭环的开发资源。

## 7. 核心用户流程

### 7.1 首次使用

```text
打开应用
  → 简短价值说明
  → 同意隐私政策和必要授权
  → 进入拍摄/上传页
  → 拍照或选择全身照
  → 质量检查
  → 确认生成
  → 等待/查看生成进度
  → 查看今日 OOTD
  → 自动记录到今天
  → 保存或分享
```

建议在用户看到第一个生成结果后，再完成非必要的资料补充。若技术方案允许匿名试用，可把账户注册延后到保存或跨设备同步前。

### 7.2 日常使用

```text
打开应用
  → 默认进入今日页或拍摄入口
  → 拍照/上传
  → 确认照片
  → 生成
  → 查看结果
  → 自动保存
  → 分享或退出
```

### 7.3 历史回顾

```text
进入记录页
  → 日历或时间线浏览
  → 选择某一天
  → 查看 OOTD 形象与原图
  → 再次导出、分享、重新生成或删除
```

## 8. 信息架构与页面需求

MVP 建议采用三个一级入口：首页/今日、记录、我的。拍摄按钮应始终明显可见。

### 8.1 今日页 / 拍摄页

**目标**：让用户以最少步骤开始一次记录。

必须包含：

- “拍摄今日 OOTD”主按钮；
- “从相册选择”入口；
- 简洁的全身取景示例；
- 当天已有记录时展示今日结果；
- 新建或重新拍摄入口；
- 相机和相册权限被拒绝时的恢复指引。

拍摄提示：

- 保持完整身体和鞋子进入画面；
- 光线充足；
- 手臂与身体适当分开；
- 避免多人、严重遮挡和强烈逆光；
- 在不影响体验的前提下使用轮廓框和实时提示。

### 8.2 照片确认页

必须包含：

- 图片预览；
- 重新拍摄/重新选择；
- 开始生成按钮；
- 对明显不合格照片给出具体原因；
- 简明提示：照片会被用于生成和保存，可在设置中删除。

质量检查至少覆盖：

- 是否存在且仅存在一个主要人物；
- 是否基本为全身照；
- 清晰度是否满足要求；
- 是否严重过暗、过曝或被遮挡；
- 图片格式、尺寸和文件大小是否支持。

质量不理想但仍可尝试时，允许用户继续；确定无法生成时才阻止提交。

### 8.3 生成进度页

必须包含：

- 明确的进行中状态；
- 不使用虚假精确百分比；
- 预计耗时区间（只有后端有可信依据时才显示）；
- 用户切到后台后任务继续执行；
- 失败原因和重试入口；
- 取消任务入口（若服务端能力支持）；
- 生成时间较长时允许用户离开，完成后通过应用内状态或通知返回结果。

任务状态建议：`queued`、`processing`、`succeeded`、`failed`、`cancelled`。

### 8.4 OOTD 结果页

**目标**：提供产品的“惊喜时刻”。

必须包含：

- 今日生成形象的主视觉展示；
- 日期；
- 用户通过手势在允许范围内主动转动模型；
- 保存到系统相册；
- 分享；
- 重新生成；
- 查看原图；
- 删除记录；
- 清楚区分原图和 AI 处理/建模结果。

视觉要求：

- 结果整体风格统一、精致，具有数字收藏品或 OOTD 手办感；
- 优先保留发型、人物整体辨识度、服装轮廓、主色、主要图案、鞋包和明显配饰；
- 不主动夸张或贬损用户体型；
- 对照片不可见区域进行合理补全，但不宣称精确还原；
- 结果不满意时支持重新生成，并说明重新生成可能产生差异。

### 8.5 记录页

必须包含：

- 月历视图，已记录日期有明确标识；
- 时间线视图，按日期倒序展示；
- 点击记录进入详情；
- 空状态引导用户创建第一条记录；
- 加载、失败和无网络状态。

MVP 默认每个日期显示一个主记录。数据层应保留未来支持同日多条记录的可能性。

### 8.6 分享导出页

P0 支持静态 OOTD 分享卡片。短动态分享内容属于 P1，不作为本地建模 PoC 和首版 MVP 的阻塞项。

分享内容默认包含：

- 生成的 OOTD 形象；
- 日期；
- 克制的产品标识。

默认不包含：

- 原始照片；
- 精确位置；
- 用户真实姓名；
- 其他隐私信息。

用户应可以先预览，再调用系统分享面板或保存至相册。导出失败时提供重试。

### 8.7 我的 / 设置页

必须包含：

- 账户状态；
- 隐私政策和用户协议；
- 相机、相册、通知权限状态；
- 原图保存策略说明；
- 删除单条内容和删除账户入口；
- 退出登录；
- 意见反馈入口。

## 9. 功能需求明细

### FR-01 图片输入

- 支持调用系统相机拍摄；
- 支持从相册选择一张图片；
- 支持常见移动端图片格式；
- 上传前进行必要的压缩、方向纠正和元数据处理；
- 不因压缩导致服装纹理完全丢失；
- 上传失败可重试，不重复创建多条记录。

### FR-02 质量检查

- 在客户端或服务端检测图片是否适合生成；
- 提示应说明具体问题和改善方法；
- 对边缘情况允许用户确认后继续；
- 质量检查结果需要记录，用于分析生成失败原因。

### FR-03 生成任务

- 每次提交产生唯一任务 ID；
- 任务状态可查询，并支持幂等重试；
- App 退出或网络中断后重新进入，仍能恢复任务状态；
- 同一用户的重复点击不能产生不可控的重复扣费或重复任务；
- 服务端保存模型版本、建模管线版本和处理参数版本，方便结果追踪；
- 生成失败不能创建看似成功但内容缺失的 OOTD 记录。

### FR-04 结果展示

- 支持展示生成资产和低清预览；
- 资源加载时显示占位状态；
- 立体交互在主流目标设备上保持流畅；
- 无法加载 3D/动态资产时，使用静态预览作为保底；
- 用户可查看生成时间和对应日期，但无需展示技术参数。

### FR-05 记录管理

- 生成成功后自动创建当日记录；
- 记录与原图、生成资产、分享资产关联；
- 用户可以删除整条记录；
- 若允许单独删除原图，删除后不影响已明确保留的生成结果；
- 删除后的缓存、缩略图和云端文件应按隐私策略清理；
- 跨时区时以用户创建记录时的本地日期为准，并保存时区信息。

### FR-06 重新生成

- 用户可以基于原图重新生成；
- 新结果完成前保留旧结果，避免用户失去已有内容；
- 生成成功后由用户选择替换主结果，或由产品明确采用自动替换规则；
- 需要防止无限免费重试造成成本失控，具体额度由商业策略确定。

### FR-07 分享与导出

- 服务端或客户端可生成稳定的静态分享图片；
- 分享资产不包含原图隐私元数据；
- 导出分辨率满足主流社交平台浏览需求；
- 分享操作调用系统能力，不在 MVP 内自建社区；
- 记录分享事件，但不读取用户最终选择的外部联系人。

### FR-08 账户与同步

- 支持一种低摩擦登录方式；
- 用户内容与账户关联并可跨设备恢复；
- 登录失败不应丢失本地尚未提交的照片；
- 支持账户注销与数据删除申请；
- 游客模式是否启用在技术设计阶段决定，但不得导致隐私和数据归属不清。

## 10. “立体 OOTD”产品定义

### 10.1 MVP 所需体验

“立体”是面向用户的视觉体验要求，不预先锁定为某一种实现技术。MVP 最终输出需满足：

- 人物具有可感知的空间层次或体积感；
- 结果页输出可实时渲染的模型或等价可交互资产，由用户通过手势主动转动查看；
- 用户可查看的角度应根据单图重建质量设置合理边界，不强制开放完整 360°；
- 自动旋转视频或预渲染循环动画不能替代结果页的用户主动交互；
- 能够输出稳定的静态分享图；
- 在同一用户的多次生成中保持相对统一的美术风格；
- 结果的正面视觉质量优先于不可见背面的写实精度。

当前 AI 能力范围限定为图片分析、图片处理和人体/服装建模，包括人物检测、人体与服装分割、姿态估计、深度或法线估计、参数化人体拟合、穿衣人体表面重建、纹理处理、网格优化和资产导出。当前不包含生成式生图或生成式生视频需求。

### 10.2 可评估的实现路线

开发前应通过小规模技术原型比较以下路线：

1. **2.5D 几何/深度方案**：保留照片相似度，处理较快，但可转动角度有限；
2. **参数化人体模型拟合**：以 SMPL/SMPL-X 等人体网格作为姿态和形体基础，再处理外层服装；
3. **单图穿衣人体表面重建**：直接恢复人体与服装表面，立体性更强，但衣摆、头发、包袋和遮挡区域需要重点验证；
4. **混合建模方案**：结合人体拟合、深度/法线、服装表面重建、纹理投影和网格优化，输出适合移动端实时渲染的资产。

技术选型应以真实样片测试为依据，重点比较：

- 本人辨识度；
- 服装还原度；
- 美观度；
- 用户可转动范围及侧面稳定性；
- 单次耗时；
- 单次成本；
- 失败率；
- 移动端资源大小和渲染性能。

MVP 不要求从单张照片得到精确、写实、完整的 360° 数字孪生。

## 11. 非功能需求

### 11.1 性能

- 首页和历史记录的常用内容应优先使用缩略图及缓存；
- 图片上传支持弱网重试；
- 生成任务采用异步流程，不能依赖 App 持续停留在前台；
- 首个可看预览应尽可能快，高质量结果可后续替换；
- 3D 或动态展示不能导致主流目标设备明显卡顿、过热或闪退；
- 分享导出期间要有明确状态，避免用户重复点击。

生成耗时目标需要在模型技术验证后确定。产品不能使用与真实进度无关的假百分比。

### 11.2 可用性

- 核心流程单手可完成；
- 主要按钮和状态文字清晰；
- 权限被拒绝、网络异常和生成失败均有恢复路径；
- 同一次任务不会因为返回、刷新或重复点击而丢失；
- 所有不可逆删除动作均需确认。

### 11.3 兼容性

- 优先确定 iOS 或跨平台首发策略；
- 开发前明确最低系统版本、目标机型和相机权限行为；
- 若使用 WebView/WebGL/原生 3D 引擎，必须在低端目标设备进行真机验证。

### 11.4 可观测性

- 记录上传、质量检查、任务排队、生成、资产处理、保存和分享的关键状态；
- 错误日志不得直接包含用户原图、鉴权信息或其他敏感数据；
- 每条生成任务可通过匿名化任务 ID 追踪；
- 支持按模型版本分析成功率、耗时和用户重新生成率。

## 13. 隐私、安全与内容治理

### 13.1 隐私要求

- 清楚说明照片用于何种生成目的、保存多久、是否用于模型训练；
- 未经用户明确同意，不将原图或生成结果用于模型训练；
- 原始照片和生成内容默认私密；
- 分享前提供预览，默认移除位置等元数据；
- 用户可删除单条记录、原图、生成结果及整个账户；
- 数据传输和云端存储使用行业通行的加密措施；
- 对内部访问实施最小权限与审计；
- 明确第三方 AI 服务的数据处理范围和保留政策。

### 13.2 安全与滥用防护

- 仅允许用户上传有权处理的照片；
- 建立未成年人、裸露、色情、暴力和非法内容的检测及处理策略；
- 防止将产品用于未经同意的他人换装或侮辱性生成；
- 对文件类型、大小、解码和上传地址进行安全校验；
- 服务端鉴权必须确保用户只能访问自己的私密资产；
- 分享链接若存在，应支持失效和撤销。

## 15. 核心验收标准

### AC-01 完成首次记录

给定一位新用户已同意必要权限，当其拍摄或选择一张合格全身照并提交后，系统应创建生成任务；任务成功后展示 OOTD 结果，并在用户当地日期下创建记录。

### AC-02 不合格照片处理

当图片不存在主要人物、严重模糊或缺失大部分身体时，系统应明确指出问题，并提供重新拍摄或重新选择入口，不能只显示笼统错误。

### AC-03 异步任务恢复

当用户在生成过程中退出页面或关闭 App，再次进入后应能恢复任务状态，并在成功时进入对应结果，而不是要求重新上传。

### AC-04 生成失败恢复

当图片处理或建模服务失败时，原图和任务信息不应丢失；用户应看到可理解的失败状态，并可安全重试，且重复操作不会产生重复记录。

### AC-05 历史记录

生成成功的记录应出现在正确日期的日历和时间线中；用户点击后可查看结果、原图和可用操作。

### AC-06 分享

用户可以预览并导出一张不包含原图隐私信息的静态分享卡片；失败时可以重试。

### AC-07 删除

用户删除整条记录并确认后，该记录不再出现在日历和时间线中，相关云端资产按产品隐私策略进入删除流程，其他记录不受影响。

### AC-08 权限与私密性

未经身份验证或授权的用户不能访问其他用户的原图、生成结果和历史记录；新建内容默认不公开。

## 16. 风险与应对

| 风险 | 影响 | MVP 应对 |
|---|---|---|
| 单张照片无法准确恢复背面 | 用户认为“不像” | 明确采用风格化/有限角度展示，不承诺精确 360° 复刻 |
| 生成结果不稳定 | 降低留存和分享 | 做输入质量检查、风格约束、失败保底和重新生成 |
| 生成耗时过长 | 用户中途退出 | 异步任务、快速预览、后台继续和完成通知 |
| 单次生成成本过高 | 商业上不可持续 | 比较多条技术路线，记录成本，限制滥用和重试次数 |
| 用户对脸和体型敏感 | 负面情绪与投诉 | 不做身体评价，提供风格预期说明和删除/重生成能力 |
| 原图与人脸数据泄露 | 严重信任和合规风险 | 默认私密、加密、最小权限、可删除、第三方数据政策审查 |
| 分享内容缺乏传播力 | 难以自然增长 | 先把静态分享卡片作为 P0 做到稳定、精致，再通过数据决定是否加入动态分享 |

## 17. 建议开发阶段

### 阶段 A：视觉与技术可行性原型

- 收集获得明确授权的代表性测试照片；
- 对比 2.5D 几何、参数化人体拟合、单图穿衣人体重建和混合建模路线；
- 产出一组可供用户盲测的样片；
- 测量耗时、成本、失败率和服装还原度；
- 确定 MVP 的“立体”标准与输出格式。

### 阶段 B：可点击产品原型

- 完成拍摄、确认、生成中、结果、记录和分享的完整交互；
- 验证用户是否理解产品、能否独立完成流程；
- 验证用户主动转动模型的交互和静态分享卡片的视觉方向。

### 阶段 C：MVP 工程实现

- 账户、上传、生成任务、记录、资产和分享链路；
- 异步状态恢复与异常处理；
- 隐私、删除和基础内容安全；
- 分析埋点与生成成本监控。

### 阶段 D：小范围测试

- 邀请目标用户连续使用 7–14 天；
- 重点观察第二次记录行为，而非只看首次生成反馈；
- 根据“好看、像本人、像衣服、等待是否值得”调整生成方案；
- 核心闭环验证成功后，再评估数字衣橱和自由搭配。

## 18. 开发前待确认事项

以下问题不改变产品目标，但会影响具体实施：

1. 首发平台：iOS、Android、Web，还是跨平台 App；
2. 首发地区及其隐私、内容治理和支付要求；
3. OOTD 形象的最终视觉风格；
4. 允许的最大生成时长和单次成本；
5. 是否提供匿名试用；
6. 原图默认长期保存，还是用户可选择生成后自动删除；
7. 免费用户的每日生成和重新生成额度；
8. 静态分享卡片的比例、分辨率和品牌水印规则；
9. 第一版采用自研、开源模型、第三方 API，还是组合方案；
10. 是否需要在首版支持中国大陆手机号、Apple 登录或其他登录方式。

## 19. 后续方向（非 MVP 承诺）

核心闭环获得验证后，可以按用户真实需求逐步探索：

```text
每日 OOTD 记录
  → 从历史照片识别重复服装
  → 自动形成数字衣橱
  → 使用多日素材建立更稳定的个人数字人
  → 自定义搭配
  → 电商链接导入
  → 虚拟试穿与品牌合作
```

任何后续功能都应以是否增强“记录—回顾—分享”闭环为判断依据，避免过早把产品扩展成复杂的衣橱管理系统。

## 20. 已确认的本地实验硬件与边界

### 20.1 GPU 基线

- 本地图片处理和人体/服装建模 PoC 使用单张 **NVIDIA RTX 3090（24GB 显存）**；
- 该配置作为技术路线筛选和端到端实验的目标运行环境；
- PoC 方案应能在单卡环境中依次完成人物检测与分割、姿态/深度/法线估计、人体与服装建模、纹理处理、网格优化和模型资产导出；
- 可以通过分阶段加载、混合精度和合理降低实验分辨率控制显存，不要求多个模型同时常驻 GPU。

### 20.2 当前计算范围

- 当前以预训练模型推理、传统图像处理、几何重建和模型后处理为主；
- 当前不计划训练大型基础模型，也不包含生成式生图或生成式生视频；
- 用户手动转动模型属于客户端实时渲染与交互，不属于视频生成任务；
- 如果某条候选路线仅能依靠高于 24GB 显存的单卡才能完成基本推理，应说明收益，并优先寻找可在 RTX 3090 上运行的替代或优化方案。

### 20.3 待软件选型后确定

- 主机操作系统及开发环境；
- CUDA、PyTorch和相关原生依赖版本；
- 系统内存和本地存储容量基线；
- 具体人体/服装重建模型、模型许可证和商用限制；
- 最终交互资产格式、面数、贴图规格与移动端渲染方案。

## 21. 当前实施阶段：本地桌面原型

### 21.1 阶段决策

在进入移动端、跨平台客户端或完整云端系统前，项目先实现本地桌面原型，用于验证图片处理、人体/服装建模和用户主动转动模型这一核心体验。

桌面原型采用本地 Web 形态，而不是立即开发传统原生桌面应用：

- React、TypeScript 和 Three.js 实现界面与实时模型查看；
- Python、FastAPI、PyTorch 和 CUDA 实现图片处理、任务管理与建模；
- SQLite 保存本地项目和任务状态；
- 本地文件系统保存原图、中间产物、GLB、预览图、日志和实验指标；
- 用户通过本机浏览器访问原型；
- 核心验证成功且确有安装包需求后，再评估使用 Tauri 包装。

### 21.2 本阶段优先验证

- 单张照片的人体和服装重建质量；
- 用户主动转动模型的体验价值；
- 可靠的最大左右转动角度；
- RTX 3090 上的处理耗时、显存和失败率；
- GLB 的面数、贴图、体积、加载速度和渲染流畅度；
- 轻量有限角度方案与完整穿衣人体网格方案的投入产出差异。

### 21.3 本阶段暂不投入

- iOS、Android、React Native 或 Flutter；
- 云端账户和跨设备同步；
- PostgreSQL、Redis、对象存储和云端任务队列；
- 相机权限、推送通知和手机分享链路；
- Electron 或 Tauri 桌面安装包；
- 多用户线上部署与商业化能力。

桌面原型是技术可行性和核心体验验证工具，不等同于完整 MVP。详细技术设计、软件栈、目录结构、任务状态和验收标准见 `docs/DESKTOP_PROTOTYPE_TECH_STACK.md`。
